# Задание Nuclear IT Hack в ноябре 2026

Vexto должен стать Android-приложением для полностью локальной расшифровки разговоров с разделением говорящих, временными метками, просмотром и экспортом результата. В обязательные требования входит **локальная LLM**; одного распознавания речи недостаточно. На точность транскрибации и диаризации приходится 65 из 100 баллов.

Источник: презентация «Хахатон Ноябрь 2026.pdf», 23 слайда, титульное название «Некйро-стенографист», Nuclear IT Hack. Конспект подготовлен 6 ноября 2026. Номера слайдов ниже относятся к этому PDF. Это изложение задания и рабочие выводы для проекта; конкретные модели и архитектура пока не выбраны.

## Обязательная функциональность

По слайдам 8–9 и 17 требуется:

- Работающее Android-приложение, предоставляемое в виде APK.
- Импорт аудиофайла из локального хранилища устройства.
- Использование локальной LLM.
- Преобразование речи в текст.
- Автоматическое определение и разделение говорящих — диаризация.
- Временные метки для реплик.
- Структурированная расшифровка с идентификаторами участников.
- Просмотр расшифровки внутри приложения.
- Экспорт результата в файл.

Все этапы обработки выполняются непосредственно на Android-устройстве. Слайд 14 допускает вход как из локального файла, так и запись из интерфейса приложения. При этом импорт явно обязателен по слайду 9; запись с микрофона не заменяет импорт и отдельно не перечислена как обязательная функция.

## Ограничения обработки

Слайды 10–11 запрещают:

1. Передавать аудиозаписи внешним сервисам для распознавания.
2. Использовать облачные API для транскрибации, диаризации или обработки текста.
3. Вычислять результат на удалённом сервере или компьютере.
4. Подменять работу модели заранее подготовленной расшифровкой.

Основная задача должна работать без интернета. Все необходимые модели должны находиться на устройстве к моменту проверки. Готовые модели и библиотеки разрешены.

Практический вывод для разработки: модельный конвейер приложения нужно проверять в офлайн-режиме целиком, включая инициализацию моделей и экспорт. Работа с Android-эмулятором через ADB — инструмент разработки; перенос инференса на компьютер вместо Android-приложения не соответствует заданию.

## Контракт результата

По слайдам 14–15 экспортируется JSON следующей структуры:

```json
{
  "transcript": [
    {
      "speaker_id": "speaker_1",
      "start_ms": 1250,
      "end_ms": 4380,
      "text": "Добрый день!"
    }
  ]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `transcript` | array | Массив реплик |
| `speaker_id` | string | Идентификатор говорящего |
| `start_ms` | integer | Время начала реплики в миллисекундах |
| `end_ms` | integer | Время окончания реплики в миллисекундах |
| `text` | string | Текст реплики |

Идентификаторы обозначают говорящих, а не обязательное распознавание настоящих имён людей. Внутренние форматы хранения команда выбирает сама, но внешний JSON-контракт задан презентацией.

## Как проверяют решение

Слайд 16 описывает единый для всех команд порядок:

1. Эксперты устанавливают заранее предоставленный APK.
2. Импортируют тестовые записи диалогов.
3. Запускают транскрибацию и диаризацию.
4. Экспортируют результаты.
5. Сравнивают их с эталонными расшифровками.
6. Рассчитывают WER и RTF.

Все команды получают одинаковые тестовые данные. Точные формулы пересчёта метрик в баллы и правила сопоставления говорящих в презентации не раскрыты.

Термины для команды: WER обычно означает долю ошибок распознавания слов; RTF — отношение времени обработки к длительности аудио. Это пояснение терминов, а не опубликованная в презентации методика оценки.

## Критерии оценки

Слайд 22:

| Критерий | Максимум баллов |
|---|---:|
| Точность транскрибации | 40 |
| Точность диаризации | 25 |
| Точность временных меток | 10 |
| Скорость обработки | 10 |
| Работоспособность и UX | 10 |
| Защита решения | 5 |
| **Итого** | **100** |

Вывод для приоритетов: сначала обеспечить рабочий обязательный сценарий, затем улучшать распознавание, диаризацию и границы реплик. Эти три критерия дают 75 баллов; улучшения внешнего вида не должны отнимать время у их работоспособности и качества.

## Дополнительные возможности

Слайд 18 — средний уровень, дополнительно к обязательному сценарию:

- Предварительная обработка аудиосигнала.
- Фильтрация пауз и неречевых фрагментов.
- Устойчивое определение участников при смене реплик.
- Восстановление пунктуации.
- Прогресс обработки.
- Воспроизведение аудио с переходом к соответствующей реплике.

Слайд 19 — продвинутый уровень:

- Обработка фонового шума и некачественных записей.
- Распознавание коротких реплик и перебиваний.
- Обработка одновременной речи нескольких участников.
- Устойчивость к различиям тембра и манеры речи.
- Оптимизация использования RAM.
- Аппаратное ускорение инференса на устройстве.
- Редактирование и повторная обработка отдельных фрагментов.

Это примеры улучшений, а не дополнительные обязательные пункты. Отдельных фиксированных бонусов за каждую функцию презентация не устанавливает.

## Что команда выбирает самостоятельно

Слайды 12–13 разрешают использование ИИ как инструмента, но требуют глубокого понимания решения участниками. Команда определяет:

- Модели ASR, диаризации и LLM.
- Архитектуру приложения и интеграцию моделей с Android.
- Предварительную и последующую обработку аудио.
- Определение границ реплик.
- Внутреннее хранение данных.
- Пользовательский интерфейс.
- Способы повышения точности и производительности.

Роль LLM не конкретизирована. Нельзя считать ASR автоматическим выполнением требования «локальная LLM»: нужно выбрать и объяснить отдельную роль либо обосновать соответствие выбранной модели этому требованию.

## Применение к Vexto

Ниже — рабочие выводы и ранее согласованные настройки, а не дополнительные условия со слайдов:

- Основная ветка разработки — `dev`; правила команды находятся в `AGENTS.md`.
- Проверять на Android-эмуляторе с **4 ГБ RAM**. Это отдельное требование пользователя из чата, в презентации объём RAM не указан.
- Уже настроенный профиль — Pixel 7 со штатным экраном 1080 × 2400, 420 dpi. Навык работы через SDK и ADB: [android-emulator](../.agents/skills/android-emulator/SKILL.md).
- Для повседневной работы агента предпочтителен запуск без окна; видимое окно — по запросу пользователя.
- Контрольный сквозной сценарий: установить APK → отключить интернет → импортировать неизвестную запись → реально выполнить локальные модели → увидеть реплики, говорящих и времена → экспортировать валидный JSON.
- При выборе моделей оценивать не только размер файлов, но и пиковую RAM всего приложения и время обработки на целевом Android-окружении.
- Для собственных тестов предусмотреть сравнение с эталоном, замер времени, проверку JSON и устойчивости идентификаторов говорящих. Числовые пороги качества ещё нужно согласовать.

## Что уточнить у организаторов

Презентация не задаёт следующие параметры, поэтому их нельзя считать уже известными:

- Дедлайн сдачи APK, материалов и время защиты.

- Язык речи, длительность и форматы аудио, число говорящих.
- Точная роль локальной LLM и критерий её достаточного использования.
- Нормализация текста для WER, формула баллов и методика оценки диаризации, временных меток и RTF.
- Порядок доставки моделей на устройство: отдельно или внутри APK, лимиты размера APK и моделей.
- Есть ли дополнительные требования к лицензиям моделей и библиотек.
