# Модуль `:llm`: локальная LLM

Офлайн-модель на устройстве для вспомогательных задач над готовым транскриптом:

- `title`: короткое название разговора для списка на «Главной»;
- `speakerNames`: имена участников, если они прямо прозвучали в речи;
- `summary`: краткая сводка и ключевые пункты со ссылками `[mm:ss]` на реплики.

Текст транскрипта, по которому считается WER, модуль не меняет: модель только читает его.

## Архитектура

```
UI-процесс                                   процесс :llm
LlmClient ── AIDL (ILlmService) ──────────►  LlmService ── JNI ──► llama.cpp
  промпты, нарезка на куски,     ◄── поток     одна модель, один запрос за раз,
  проверка ответов                  токенов    выгрузка после простоя
```

- **Отдельный процесс.** `LlmService` объявлен с `android:process=":llm"`. Падение натива (SIGILL, OOM, ошибка llama.cpp) убивает только этот процесс: текущий вызов в UI завершается `LlmException`, следующий вызов поднимает сервис заново.
- **llama.cpp** закреплён на теге `v0.7.0`. Исходники не хранятся в git: `scripts/fetch_llama_cpp.sh` скачивает архив тега и сверяет sha256. Gradle запускает скрипт сам перед первой сборкой (`fetchLlamaCpp` → `preBuild`), поэтому чистый клон собирается одной командой (нужна сеть для первой загрузки, NDK 28.2 и CMake 3.22.1 из SDK). Каталог `llm/third_party/` в `.gitignore`.
- **Сборка натива:** CMake через `externalNativeBuild`, ABI `arm64-v8a` и `x86_64`, всегда Release (в Debug llama.cpp медленнее в десятки раз), NDK r28: все `.so` выровнены по 16 КБ. Собирается только библиотека `llama` и CPU-бэкенды, без examples/server/tools.
- **Выбор SIMD без SIGILL.** CPU-бэкенд ggml собран в нескольких вариантах (`GGML_BACKEND_DL`, `libggml-cpu-<вариант>.so`). Вариант выбирает наш JNI по флагам `/proc/cpuinfo` и грузит его через `ggml_backend_load`, а встроенный подсчёт ggml не используется: тот не проверяет поддержку AVX со стороны ОС и на гипервизоре может выбрать AVX2-сборку. Ядро Linux убирает `avx`/`avx2` из `/proc/cpuinfo`, если ОС не сохраняет эти регистры.

  | ABI | порядок попыток | условие |
  |---|---|---|
  | x86_64 | `haswell` | `avx avx2 fma f16c bmi2` |
  | | `sandybridge` | `avx` |
  | | `sse42` | `sse4_2` |
  | | `x64` | всегда |
  | arm64-v8a | `android_armv8.6_1` | `asimddp asimdhp i8mm` |
  | | `android_armv8.2_2` | `asimddp asimdhp` |
  | | `android_armv8.2_1` | `asimddp` |
  | | `android_armv8.0_1` | всегда |

  Остальные варианты (AVX-512, SVE, SME) исключены из APK. Принудительный вариант: `LlmConfig(cpuVariant = "sse42")` или аргумент теста `-e cpuVariant sse42`.
- **Шаблон чата** берётся из GGUF (`llama_model_chat_template` + `llama_chat_apply_template`). Для Qwen3 в начало ответа добавляется пустой блок `<think>\n\n</think>`: так шаблон модели отключает рассуждения при `enable_thinking=false`.
- **JSON-ответы** ограничены GBNF-грамматикой, поэтому всегда разбираются. В сводке грамматика разрешает только метки времени, которые есть во входном куске.

## Защита от галлюцинаций

- Модель возвращает список «имя → участник», код оставляет имя, только если оно буквально встречается в репликах (без учёта регистра, окончание допускается: «Барсик» засчитывается по «Барсику»).
- Имя принадлежит участнику, если он представился («меня зовут», «я», «это» перед именем) или если имя произносят только другие. Если участник сам произносит имя без представления, он обращается к кому-то, и такое имя ему не присваивается.
- Приветствия и обращения к группе («Привет», «Коллеги») не принимаются за имена. У участника одно имя, одно имя (с учётом окончаний) у одного участника.
- Пункт сводки с меткой времени, которой нет во входе, отбрасывается.
- Название: одна строка, 3–60 символов, без кавычек и точки.

## Использование

Модель берётся из assets модуля (см. «Модель») и при первом вызове копируется в `filesDir/models/`: llama.cpp читает веса через mmap по пути к файлу, а файл внутри APK так открыть нельзя.

Kotlin:

```kotlin
val llm = LlmClient(context)                     // LlmConfig() по умолчанию
val transcript = listOf(
    Utterance("speaker_1", 1_000, 4_200, "Меня зовут Мурзик, начнём планёрку."),
    Utterance("speaker_2", 4_900, 8_000, "Привет. Макеты почти готовы."),
)
lifecycleScope.launch {
    val title = llm.title(transcript)            // String?
    val names = llm.speakerNames(transcript)     // {speaker_1=Мурзик, speaker_2=null}
    val summary = llm.summary(transcript)        // Summary(text, points[timestamp, startMs, text])
}
// Поток токенов для произвольного запроса; отмена коллектора отменяет генерацию.
llm.stream("Перечисли задачи из стенограммы:\n...").collect { piece -> append(piece) }
llm.close()                                      // в onDestroy
```

Java (колбэки приходят в главном потоке):

```java
LlmClient llm = new LlmClient(context);
LlmClient.Call call = llm.titleAsync(transcript, new LlmClient.Callback<String>() {
    @Override public void onSuccess(String title) { titleView.setText(title); }
    @Override public void onError(Throwable error) { /* показать «не удалось» */ }
});
// call.cancel();  llm.close();
```

`Utterance(speakerId, startMs, endMs, text)` повторяет поля экспорта движка (`speaker_id`, `start_ms`, `end_ms`, `text`), поэтому транскрипт из `:engine` переводится в этот тип одной строкой `map`.

Вызовы выполняются по очереди: сервис держит одну модель и обрабатывает один запрос за раз.

## Память и потоки

- Контекст `n_ctx = 4096`, KV-кэш в `q8_0` (с flash attention): вдвое меньше `f16`.
- Веса только в mmap: перепаковка весов под SIMD (`use_extra_bufts`) по умолчанию выключена. Она копирует модель в анонимную память: на Qwen3-0.6B анонимная часть RSS растёт с 361 до 965 МиБ, а prefill на эмуляторе быстрее не становится (см. «Замеры»). Включается через `LlmConfig(repackWeights = true)`.
- Потоки: `min(4, ядер)`; меняется через `LlmConfig(threads = …)`.
- Модель грузится при первом запросе и выгружается через `idleUnloadMs` (60 с) простоя, по `onTrimMemory(RUNNING_LOW и выше)` и по `ILlmService.unload()`.
- Длинный транскрипт режется по репликам на куски, которые помещаются в контекст (токены считает сам токенизатор модели). `speakerNames` проходит куски по очереди, `summary` делает сводку каждого куска и затем объединяет их, `title` смотрит первый кусок.
- Не запускайте LLM одновременно с распознаванием: потоки ggml ждут друг друга в активном цикле, и при занятых ядрах генерация падает в десятки раз (см. замеры).

## Модель

```sh
scripts/fetch_llm_model.sh            # Qwen3-0.6B Q8_0, 639 МБ
scripts/fetch_llm_model.sh qwen2.5    # Qwen2.5-0.5B-Instruct Q4_K_M, 491 МБ
./gradlew :app:assembleDebug
```

Скрипт кладёт файл в `llm/src/main/assets/models/` (в `.gitignore`, в git модели не попадают) и сверяет sha256. В APK лежит ровно одна модель. Без модели сборка проходит, а вызов вернёт `LlmException` с подсказкой.

Выбрана **Qwen3-0.6B Q8_0** (официальный GGUF, Apache-2.0). Запасная **Qwen2.5-0.5B-Instruct Q4_K_M** вдвое легче по анонимной памяти и немного быстрее, но на сводке скопировала шаблон из промпта («2-3 предложения о сути разговора»), ставила вместо пунктов «...» и один раз перенесла в сводку имя из примера в промпте. Имена участников и название обе модели находят одинаково.

## Замеры

Эмулятор `vexto4g`: Android 15 (API 35), arm64-v8a, 4 vCPU, 4 ГБ RAM, хост Apple M4 Max. Вариант бэкенда `android_armv8.2_2` (в `/proc/cpuinfo` гостя нет `i8mm`). Фикстура `LlmTasksTest`, `n_ctx 4096`, KV `q8_0`, температура 0,2, seed 42: при одинаковых настройках ответы повторяются слово в слово. Хост во время замеров был нагружен соседними сборками (load average около 50), поэтому разброс скорости между прогонами достигает 2 раз; в таблице прогоны при простое эмулятора.

| Модель, настройки | prefill, ток/с | генерация, ток/с | загрузка | RSS / анонимная часть | все 3 задачи |
|---|---:|---:|---:|---:|---:|
| Qwen3-0.6B Q8_0, 4 потока | 109–136 | 17,7–20,5 | 0,3–0,5 с (3,3 с с копированием из APK) | 1037 / 361 МиБ, пик 1089 | 37–38 с |
| Qwen3-0.6B Q8_0, 2 потока | 67–90 | 15–18 | 0,5 с | 1037 / 360 МиБ | 48 с |
| Qwen3-0.6B Q8_0, 4 потока, перепаковка весов | 117–124 | 10–17 | 2–13 с | 1638 / 965 МиБ, пик 1690 | 53–57 с |
| Qwen2.5-0.5B Q4_K_M, 4 потока | 114–123 | 14–24 | 1,3 с | 763 / 366 МиБ, пик 836 | 27 с |

Время по задачам для выбранной конфигурации (Qwen3, 4 потока): название 5,2 с (609 токенов промпта, 4 токена ответа), имена 10,8 с (627 / 96), сводка 20,9 с (701 / 254).

Что видно из замеров:
- Перепаковка весов (`repackWeights = true`) на этом эмуляторе не ускорила prefill, а добавила около 600 МиБ анонимной памяти. Поэтому по умолчанию она выключена.
- 4 потока быстрее 2 на prefill примерно в 1,4 раза, генерация почти не меняется.
- При параллельной нагрузке на CPU (на том же эмуляторе работал движок распознавания, около 150–370 % CPU) генерация падала до 0,2–1,2 ток/с, prefill до 37–54 ток/с.
- Для сравнения, Артём на x86_64-эмуляторе (Intel Core Ultra 7, 2 потока, `llama-bench`) получил 27,5–34 ток/с генерации Qwen3-0.6B Q8_0 и 695–785 МиБ RSS. Сборку x86_64 этого модуля на x86-эмуляторе ещё нужно прогнать тем же тестом.
- Падение процесса `:llm` во время генерации (`kill -9`) проверено: вызов в UI-процессе завершился `LlmException("процесс LLM завершился во время генерации")`, UI-процесс продолжил работу.

Ответы Qwen3-0.6B на фикстуре:

```

speakerNames: {speaker_1=Мурзик, speaker_2=Барсик, speaker_3=null}

  сроки для проверки макетов. После этого спрашивают о разделах отзывов и времени на финальную проверку.
  [00:01] Мурзик приветствует, обсуждает план встречи.
  [00:08] Барсик уточняет, что макеты готовы.
  [00:14] Мурзик спрашивает о времени для проверки мобильной версии.
  [00:26] Барсик уточняет, что ссылки на проекты будут заменены в пятницу.
```

## Проверка на устройстве

Инструментальный тест `LlmTasksTest` прогоняет три задачи на фикстуре (15 реплик, три участника, два имени звучат в речи) через процесс `:llm` и печатает время, ток/с и RSS.

```sh
./gradlew :llm:assembleDebugAndroidTest
adb install -r -t llm/build/outputs/apk/androidTest/debug/llm-debug-androidTest.apk

# Модель в filesDir тестового приложения: к файлам, залитым adb в Android/data, приложение доступа не имеет.
adb push Qwen3-0.6B-Q8_0.gguf /data/local/tmp/model.gguf
adb shell run-as com.vexto.llm.test mkdir -p files
adb shell "run-as com.vexto.llm.test sh -c 'cat > files/model.gguf' < /data/local/tmp/model.gguf"
adb shell rm /data/local/tmp/model.gguf

adb shell am instrument -w -e class com.vexto.llm.LlmTasksTest \
    com.vexto.llm.test/androidx.test.runner.AndroidJUnitRunner
# другая модель или вариант CPU:  -e modelPath /data/user/0/com.vexto.llm.test/files/other.gguf  -e cpuVariant sse42
# прочие аргументы:  -e threads 2  -e repack true
```

Если перед сборкой запустить `scripts/fetch_llm_model.sh`, модель попадёт в тестовый APK, и копировать её вручную не нужно: `-e modelPath asset` проверяет тот же путь, что и приложение (копирование из APK в `filesDir/models/`).

Не используйте `connectedDebugAndroidTest`: он удаляет тестовое приложение вместе с моделью после прогона.

Юнит-тесты разбора ответов: `./gradlew :llm:testDebugUnitTest`.

## Известные ограничения

- **x86_64 не проверен на устройстве.** Сборка проходит, базовые библиотеки (`libllama`, `libggml*`, `libvexto_llm`, варианты `x64` и `sse42`) не содержат AVX-инструкций (проверено `llvm-objdump`, 0 обращений к `ymm`), но прогон `LlmTasksTest` на x86_64-эмуляторе ещё нужен.
- **Параллельная нагрузка.** Если в это время работает ASR или диаризация, генерация замедляется в десятки раз. Запускать задачи LLM после распознавания.
- **Качество 0,6B.** Название бывает из одного слова («Макеты»), в пунктах сводки встречаются ошибки атрибуции. Имя третьего участника, которое не прозвучало, остаётся `null`, как и должно.
- **Сжатие модели в APK.** `androidResources.noCompress` из библиотеки не переносится в APK приложения, поэтому в `app-debug.apk` модель лежит сжатой (Deflate, 4 % выигрыша). Копирование при первом запуске работает и так; чтобы файл хранился без сжатия, добавьте `'gguf'` в `androidResources { noCompress ... }` модуля `:app`.
- **Размер APK:** модель 639 МБ, нативные библиотеки около 21 МБ на оба ABI. После первого запуска модель занимает ещё 639 МБ в `filesDir`.
- **Один запрос за раз.** Сервис выполняет запросы последовательно; отмена (`Call.cancel()` или отмена корутины) прерывает генерацию и prefill.
